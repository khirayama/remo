# Remo architecture

## Product loop

Remoの実装境界は`Capture → Timeline`です。

1. 通常10秒間隔、十分な静止判定後だけ5分間隔へ切り替えて位置を取得する（Webはタブ表示中のみ）。
2. 端末が写真ライブラリから撮影日時とEXIF位置を読み、最新側から段階的にTimelineへ反映する。
3. 端末内の記録を日付と時刻で並べ、地図の軌跡とTimelineへ表示する。
4. 記録は未ログインでも端末へ保存し、認証済みユーザーだけが記録メタデータと縮小写真をAPIへバックアップする。

認証はTimelineの利用条件ではなく、バックアップのための機能です。起動時はログイン画面へ遷移せず、設定からユーザーがバックアップを開始します。ログアウトしても端末内の記録は残し、別端末やWebでの閲覧はログイン後に行います。

## Data model

1件のTimeline recordは次の情報だけを持つ。

- `id`
- `startedAt`
- `latitude` / `longitude`（任意）
- `originalLatitude` / `originalLongitude`（写真の元のEXIF座標、任意）
- `locationSource`（写真の位置の由来。`exif` / `inferred` / `manual` / `removed`、任意）
- `photoLocationAutoPlacementDisabled`（元のEXIFへ明示的に戻した写真の自動表示配置を無効化、任意）
- `mediaType`（写真イベントの種別。`photo` または `video`、旧データは写真として扱う）
- `photoCount`
- `source`（`location` または `photo`）
- `updatedAt`

写真・動画の記録は、同じ場所（座標を小数点以下4桁に丸めた約11m単位）・同じ種別で、直前の1枚から30分以内に撮影されたものを1件にまとめる（開始時刻は最初の1枚）。以前は端末の現地日付ごとに1件へまとめていたため、同じ場所の朝と夜の写真が夜の時刻に表示され、タイムゾーンが変わると同じ写真が別のIDになっていた。写真ごとに前回割り当てた記録IDを端末内に保持し、再スキャンでも同じIDを使う（位置補正が消えない）。旧方式の記録は、旧IDを引き継いで移行する。1件の旧記録が複数のまとまりに分かれた場合、IDを引き継がなかったまとまりは旧記録の位置補正を引き継ぐ。新しい写真だけのまとまりのIDは、最初の1枚のUTC時刻・座標・種別から決まる。写真ライブラリ全体へのアクセスがあり、スキャンが完了した場合だけ、写真がなくなった自端末の写真記録を削除する。

元写真は端末内に保存する。ログイン中は写真ごとに縮小・再圧縮したJPEGを同期APIへ送り、R2へ保存する。動画本体は送らない。写真位置を補正した場合も、元のEXIF座標は保持する。未確定のEXIF写真だけは、補正済み位置ログから求めた候補を地図・Timelineの表示座標に使うが、保存座標は変更しない。元のEXIFへ明示的に戻した場合は、自動表示配置を無効化する。

## Storage

| データ | 保存先 | 備考 |
| --- | --- | --- |
| Webの記録 | IndexedDB `remo-timeline`（v2） | 1記録1行。開始時刻のインデックス（`byTime`）で選択日・エクスポート範囲だけを読み、同期状態のインデックス（`bySync`）で未バックアップの記録だけを読む。永続化（`navigator.storage.persist()`）を要求し、使用量を設定画面に表示する |
| iOSの記録 | SQLite（Application Support `remo-timeline.sqlite`） | 1記録1行、型付きの列。書き込みはバックグラウンドの直列キューで行い、読み取りは開始時刻のインデックスを使う。UI・位置記録・バックグラウンド同期は同じ`LogDatabase.shared`を使う |
| Androidの記録 | SQLite（`rem_logs.db` v4） | 1記録1行、型付きの列（以前はJSON文字列1列）。開始時刻と同期状態のインデックスを持つ |
| 未バックアップの印・削除の待ち行列・変更された日・場所名・所有アカウント | 記録と同じDB | 記録ごとに「最後にバックアップした世代（epoch）」を持ち、現在の世代より小さい記録が未バックアップ。削除は開始時刻と種別を添えて待ち行列に入れる |
| 写真の割り当て（写真→記録ID）とアップロード済み印（プレビューのdigest付き） | iOS: `remo-photo-index.sqlite`、Android: `rem_photo_index.db` | 端末固有の写真IDを含むため、端末バックアップから除外する |
| 元写真 | 端末内 | 縮小JPEGだけをR2へバックアップ |
| クラウドの位置サンプル | Cloudflare D1 `location_chunk` | ユーザーごと・6時間ごとに1行。サンプルはJSON配列`[id, startedAt, lat, lon, accuracy, clientUpdatedAt, seq]`で持つ。1リクエストの位置サンプルは通常1〜2行の読み書きで済む |
| クラウドの写真記録と削除記録 | Cloudflare D1 `life_event` | 個別に編集・削除される記録だけを1記録1行で持つ |
| 同期の連番と上限用カウンター | Cloudflare D1 `user_sync_state` | 書き込む行はすべてユーザー単位の連番（`seq`）から`updated_at`を取る。連番はコミット順に必ず増えるので、差分同期カーソルが取りこぼさない |
| 場所名 | Cloudflare D1 `place` | ユーザーが付けた名前と座標。件数が少ないので全件を読み、変更分だけを送る |
| 縮小写真のID一覧 | Cloudflare D1 `photo_preview` | アップロード時に記録し、一覧取得でR2のlist（Class A操作）を使わない |

### メモリに持つ範囲

3プラットフォームとも、メモリに持つのは選択中の1日の記録だけです（写真記録だけは件数が少なく、写真ライブラリのスキャンと照合するため全件を読む）。記録が何年分に増えても、位置サンプル1件の追加で全件を並べ替えたり、起動時に全件を読み込んだりしません。記録が変わるたびに`revision`が進み、画面は表示中の日だけを読み直します。エクスポートは1日ずつ読みながらファイルへ書き出し、インポートは2,000件ずつ保存します。

## Sync

端末を正本とし、クラウドはバックアップと他端末での閲覧のために使います。

- **アップロードするのは未バックアップの記録だけ。** 端末は「まだバックアップしていない記録」と「削除の待ち行列」だけを送る。クラウドから削除された記録を、古いコピーを持つ別の端末が送り返すことはない（以前はサーバーに削除記録を残して防いでいた）。1リクエスト最大500件、クライアントは400件ずつ送り、応答ごとに送信済みにする。
- **ダウンロードはページごとに適用する。** カーソルが無い端末は全件を主キー順（写真記録・削除記録→位置チャンク）にページングして受け取り、最後にスナップショット開始時点の連番をカーソルにする。カーソルがある端末は`/events/head`で変化を確認し、変化があれば連番順の差分を受け取る。チャンクは「カーソル以降に書かれたサンプル」だけを返す。
- **競合は新しい方が勝つ。** サーバーも端末も記録の`updatedAt`（端末時計、サーバー時刻+5分で上限）を比べる。他端末の編集は、ローカルより新しければ取り込む（Webで補正した写真位置がスマホにも届く）。
- **個別の削除は他の端末にも伝わる。** 1件ずつ削除した記録は削除記録（`deletion_propagates = 1`）になり、同期した端末は、その削除より後に編集していない限り自分のコピーも削除する。削除記録は90日後に物理削除する。
- **「すべて削除」は他の端末に伝わらない。** クラウドの行をその場で物理削除するだけで、他の端末の記録（その端末が正本）は残る。残った記録は未バックアップではないので、クラウドへ戻ることもない。
- **同じチャンクへの同時書き込み**は、読んだ版のままなら書く（楽観ロック）方式で、負けた側が読み直してマージし直す。

### 記録の所有アカウント

端末の記録は、一度に1つのアカウントへバックアップされます（所有アカウント）。未ログインのまま記録した端末で初めてログインすると、そのアカウントが所有アカウントになります。所有アカウントと違うアカウントでログインしたときは同期を止め、「このアカウントにも保存する（世代を進めて全件を未バックアップにする）」「端末の記録を削除して切り替える」「ログアウト」を選んでもらいます。確認なしに、あるアカウントの記録が別のアカウントへアップロードされることはありません。アカウントを削除したときは所有アカウントを外して世代を進めるので、次にログインしたアカウントへ全件がバックアップされます。Webは共有PCを考慮し、ログアウト時に「このブラウザの記録を削除してログアウト」を選べます。

## Capture

### iOS

初回起動時に説明画面を表示し、「記録を始める」を選ぶと位置情報の許可を確認して、許可後は自動でCore Locationを開始する。位置情報の「常に許可」があればバックグラウンドでも動作し、通常10秒間隔、直近3分の移動変位・速度・モーションによる十分な静止判定後は5分間隔へ自動で切り替える。静止モード中は測位精度を100m相当へ下げてGPSを休ませ、移動を検知すると最高精度へ戻す。大幅位置変更の監視は常に有効にし、アプリが終了された後や端末の再起動後もシステムがアプリを再起動して記録を再開する。設定から停止できる。

### Android

初回起動時に説明のダイアログを表示してから位置情報・Activity Recognition・通知の許可を確認し、許可後は通知を伴うForeground Location Serviceを自動で開始する。端末の再起動後とアプリの更新後は`BootReceiver`がサービスを再開する（バックグラウンドからの開始をOSが拒否した場合は、アプリを開くよう通知する）。通常はFused Location Providerを高精度・10秒間隔で更新し、直近の位置サンプルが静止を示すとバランスド電力・5分間隔へ切り替える。設定から停止できる。

- **静止の判定**: 途切れずに届いた直近5分以内のサンプル（精度100m以下）が6件以上・3分以上あり、その85%以上と最新3件のすべてが中央値から40m（測位精度がそれより悪ければ精度の値）以内にあること。屋内の測位はWi-FiとGPSの間で飛び、速度も不正確なので、1件の外れや速度の誤報では判定を取り消さない（速度は、1m/s超が全体の4分の1を超えたときだけ移動とみなす）。Activity Recognitionが移動の開始を報告してから10分間は、位置が止まって見えても切り替えない（信号待ちの車など）。
- **滞在の基準点**: 切り替えた時点のサンプルの中央値と精度を基準点として保持する。5分モード中は、測位が基準点から「基準点の半径＋測位精度＋50m」以上離れたときに10秒間隔へ戻す。
- **強い合図と弱い合図**: 有意な動き（significant motion）、連続した歩数（45秒以内に30歩）、Activity Recognitionの移動開始、基準点からの離脱は、すぐに10秒間隔へ戻す。端末を手に取っただけでも発火するモーション検出・単発の歩数・静止状態の終了・遅れて届いた移動開始は、省電力の測位を1回だけ取得して基準点と比べ、離れていなければ5分モードを続ける（確認は2分に1回まで）。
- **誤検知からの復帰**: 10秒間隔へ戻った後も、10分以内に同じ基準点で測位が4件・75秒そろえば5分モードへ戻る。
- **記録の間引き**: 測位の間隔は配信時刻ではなく測位時刻どうしで比べる（遅れて配信された測位の次の測位が「早すぎる」と判定され、移動中に約3回に1回の測位を落としていた）。精度100m超の測位は、直前60秒以内に精度100m以下の記録があれば保存しない（Timelineが使わないため）。
- **診断ログ**: モード変更とその根拠、移動の合図、5分ごとの集計（受信・保存・破棄した測位の数と理由、静止判定が通らなかった理由、精度と速度、5分モード中の最長の連続歩数、電池残量と充電状態、画面・Doze・バッテリーセーバーの状態）、サービスの起動・終了と前回のプロセス終了理由を、端末内の`filesDir/capture-diagnostics.jsonl`（最大約2MB、座標は含まない）へ1行1JSONで追記する。受信した測位は、保存しなかったものも含めて1件1行で`filesDir/capture-fixes.jsonl`（最大約8MB、座標は含まない）へ別に残す: 測位時刻（保存した記録の`startedAt`と同じ）、結果（`logged`・`merged`・破棄の理由）、取得元、モード、精度、速度とその精度、方位・高度の有無、配信の遅れ、直前の測位からの時間と距離。JSONエクスポートの`diagnostics.captureLog`と`diagnostics.fixLog`に期間内の行を含め、`tools/analyze-export.py`で集計できる。インポートは無視する。

### Web

初回表示時に説明のダイアログを表示し、「記録を始める」を選ぶとブラウザの位置情報許可を確認して、許可後は`getCurrentPosition`を即時実行して、その後通常10秒間隔、直近の位置変位・速度による静止判定後は5分間隔で定期取得する。ブラウザを閉じた後の取得は行わない。設定から停止できる。

## Timeline

表示対象の日付を1日単位で切り替える。選択日だけの記録を時刻順に地図へ渡し、位置ログと座標付き写真を時系列の位置サンプルとして扱う。地図には、精度フィルター（精度100m超を除外）後のスパイク補正と滞在区間の集約を行った加工済みの移動線だけを表示する。滞在判定は生座標を使わず、位置ログと写真を含む精度フィルター後のスパイク補正済み位置だけを入力にする。精度の悪い点は加工済み移動・滞在・自動ズームから除外するが、元の記録とTimeline一覧には残す。初期表示の地図範囲は加工済み位置・滞在・写真を基準にする。滞在判定は3段階で行う。(1) 連続する位置点が80m以内（測位精度が80mより悪い点は精度の値まで、最大100m）にまとまる区間を候補にする。(2) 同じ場所（中心が80m以内）に戻る候補どうしは、間がサンプルのない12時間以内の欠測（iOSは静止中に50m移動するまで更新が届かないため）、3分以内の一時的な外れ、または全点が200m以内に留まるふらつきならつなぎ、間に別の滞在があればつながない。ただし、間に精度30m以下の測位が6件・2分以上続けて場所から離れている（80m＋測位精度より遠い）場合は、ふらつきではなく外出として滞在を分ける。3サンプル以上かつ5分以上続くものだけを滞在とする。(3) 屋内ではWi-FiとGPSの測位が数百m離れた2点の間を行き来することがあるため、隣り合う滞在は、中心が200m以内、または500m以内で一方の滞在中に他方の場所の測位（補正前の座標）が2割以上混ざる場合に、間が移動でなければ1つにまとめる。間は、(2)の条件か、300mより遠い点が3割以下、または元の場所の測位が2割以上混ざっていればノイズとみなす。滞在の座標は、50m以内に最も多くの点が集まる点の周囲の中央値とし、少数の飛んだ測位に引っ張られないようにする。間のノイズ点も滞在に含めて移動線から除く。滞在の最初と最後の最大3分のうち、確定した座標から50m（測位精度がそれより悪ければ精度の値）より遠い点は、到着前・出発後の移動として滞在から外す（その日の最初と最後の点は除く）。10分以上サンプルのない移動区間は「記録なし」として扱い、Timelineでは時間の半分以上が欠測の移動を「記録なし」と表示し、地図では点線で結ぶ。Webでは滞在時間に応じた円、Android/iOSでは軽量な地図マーカーで表示する。滞在表示には開始時刻と終了時刻を使い、元の記録は変更しない。加工済み移動線は滞在内部のサンプルを省略しつつ、滞在の代表点を前後の線で共有して連続させる。現在地は端末・ブラウザの位置レイヤーで表示する。明らかな単発GPSスパイクは前後1点の補間と、移動中に直前の位置へ戻る古い測位（前後の点の間隔が2分以内で、前後を結ぶ線から200m以上かつ前後の距離の2倍・測位精度の4倍以上離れた1〜2点）の補間に加えて、前後2点ずつが100m以内に安定している場合だけ近傍中央値へ表示用座標を補正する。さらに、同じ安定クラスタへ戻る最大2サンプルの短い往復も、各点が35m以上（測位精度がある場合は精度の2倍以上）離れている場合だけ補正し、3サンプル以上続く移動や補正距離35m未満のグレーな点はそのまま残す。移動中は、直前の補正済みの点から見て前後の点を結ぶ速さの3倍（かつ3m/s以上速い）で飛び、前後を結ぶ線から60m以上（測位精度の2倍以上）離れた1〜2点も補間する（少し前にいた場所を高い精度で報告する古い測位。1点ずつ順に判定し、2つのスパイクに挟まれた正しい点を残す）。精度50m以上の測位は、前後45秒以内に精度が半分以下の測位があれば、その2点の間へ補間する。元の記録は変更しない。未確定のEXIF写真は、撮影時刻の前後15分以内にある精度100m以下の加工済み位置ログから線形補間または最近傍で求めた表示座標へ自動配置する。手動・推定・削除済み、または元のEXIFへ戻して自動配置を無効化した写真は保存座標を使う。写真は座標を持つ記録だけ地図とTimelineに表示する。加工済み移動線の濃さは現在時刻から古いほど薄くする。地図の表示位置・ズームは初回表示と日付切替時だけ自動調整し、自動記録やバックアップによる記録更新では保持する。

選択日内の滞在区間だけを、代表座標が100m以内なら表示上の同一滞在ポイントへまとめ、訪問回数ごとにセクション化する。Timelineの集約は選択日内で行い、滞在区間・位置ログ自体も統合せず保持する。滞在や「滞在した場所」の行から開く訪問履歴では、全期間の記録から、その場所の1km以内に記録がある日だけを日ごとに滞在判定し、代表座標が100m以内の滞在を新しい順に日付ごとにまとめて表示する（訪問回数・日数・合計時間付き。日付を選ぶとその日のTimelineへ移動）。Android/iOSの滞在ポイント名・住所は端末の逆ジオコーダーから都度取得し、記録や同期データには保存しない。Webは逆ジオコーディングを行わず座標を表示する。訪問履歴のシートから場所に名前（「自宅」「職場」など）を付けられ、その場所から100m以内の滞在は3プラットフォームとも座標や住所の代わりにその名前で表示する。場所名は端末に保存し、ログイン中は同期する。

### すべての滞在

地図の「日ごと／すべて」切替で、全期間の滞在を場所ごとにまとめて表示する。滞在は日ごとの滞在判定（Timelineと同じ処理）の結果を使い、全滞在を時刻順に、最も近い場所の100m以内なら同じ場所へまとめる（場所の座標は訪問の中央値）。場所は訪問回数順に並べ、全期間／1年／30日で絞り込める。地図の円は合計滞在時間の対数で大きさを、最終訪問からの経過日数で濃さを決める。場所を選ぶと訪問履歴を表示し、日付を選ぶとその日のTimelineへ移動する。Android/iOSの場所名は、一覧に表示された行だけ端末の逆ジオコーダーから取得する。「すべて」に戻ると、離れる前の地図の表示位置を復元する。

過去日の滞在判定結果は端末内の派生キャッシュにJSON文字列1件として保存する（Webは IndexedDB `remo-stay-index` に端末ストレージIDごと、Androidは `filesDir/stay-index.json` を `AtomicFile` で、iOSは Application Support の `remo-stay-index.json` をアトミック書き込みで保存）。キャッシュは同期・エクスポートせず、いつ破棄しても記録から再計算できる。記録を書き込み・削除するとき、保存層がその記録の日を「変更された日」として記録し、滞在インデックスはその日だけをDBから読んで再計算する（編集・削除・同期・インポートのどれでも同じ）。全記録を走査して変更を探すことはしない。初回（またはアルゴリズムのバージョンかタイムゾーンが変わったとき）は記録のある全日を一度だけ計算し、途中で中断しても続きから再開する。記録中の今日はキャッシュせず常に計算する。再計算は画面の応答性を保つよう、Webは短い単位に分けて、Android/iOSはバックグラウンドで実行し、記録が更新されたら中断して最新の記録でやり直す（完了済みの日は保持する）。滞在の訪問履歴も、キャッシュの準備後はこの滞在一覧から求める。全データ削除時はキャッシュも削除する。

## Privacy

- 位置情報はOS／ブラウザの許可後だけ取得し、アプリ設定から停止できる。
- 元写真・動画本体はAPIへアップロードしない。写真の縮小JPEGだけを認証済みAPI経由でR2へ保存する。
- エクスポートは開始日・終了日を指定し、期間内の位置・写真レコードを時刻・座標・位置精度・種別・枚数付きJSONで行う。写真画像本体は含めず、元の記録をそのまま確認できる。Androidは期間内の記録の診断ログ（座標を含まない）も含める。
- ローカル開発用のサンプルデータは `fixtures/timeline/` に置き、本番データや端末の保存先とは分離する。
- 全クエリは認証済みユーザーIDで限定する。
- 端末とクラウドの全記録を削除できる。
- 未ログイン時の削除は端末内だけを対象にし、ログイン時だけクラウド削除を実行する。
- 記録を1件ずつ削除すると、位置・時刻などの内容はその場で消去し、同期用のIDと更新時刻だけを削除記録（tombstone）として残す。削除記録は他の端末にも届き、その端末のコピーも削除される。
- 「すべて削除」はクラウドの行（位置チャンク・写真記録・削除記録・場所名・縮小写真の一覧）をその場で物理削除する。他の端末の記録はその端末を正本として残るが、未バックアップではないのでクラウドへ再アップロードされない。全削除を実行した端末は位置情報の記録も停止する。
- 削除記録は90日後に毎時のCron Triggerで物理削除する。期限切れのセッションとパスワード再設定用の値、削除された写真のR2画像も同じジョブで削除する。
- 写真を端末のライブラリから削除した（または別の記録へ移った）場合、その写真を含んでいた記録の「今も含まれるプレビューの一覧」を端末が送り、サーバーは一覧にないプレビューをD1とR2から削除する。削除した写真の縮小画像がバックアップに残り続けることはない。
- アカウントはパスワードを確認したうえで削除でき、クラウドのバックアップ・セッション・認証情報をすべて削除する。端末内の記録は残す。
- サインイン・新規登録・パスワード再設定・アカウント削除はIPアドレスごとにレート制限する（Workers Rate Limiting、60秒10回）。ログイン後の書き込みはアカウントごとに制限する（60秒600回）。
- 保存量には上限がある: 位置チャンク1行1.5MB・1アカウント40,000チャンク、プレビューは1記録1,000枚・1アカウント100,000枚、場所名2,000件。上限を超えた分は拒否する。
- `REQUIRE_EMAIL_VERIFICATION=true`（とメール送信設定）で、メールアドレスを確認するまでログインできないようにできる。既定はオフ。
- 別のアカウントの記録が残っている端末では、確認するまで同期しない（「記録の所有アカウント」参照）。
- Webの静的ファイルにはCSPなどのセキュリティヘッダーを付ける（ビルド時に`_headers`を生成。許可するのは自身のスクリプト、Webフォント、設定した地図タイルとAPIだけ）。
- WebはWeb自身のWorkerが`/api/*`をService BindingでAPIへ中継し、同一オリジンでAPIを使う。`*.workers.dev`はPublic Suffixのため、Web用とAPI用のworkers.devホストは別サイトになり、セッションCookieがサードパーティCookieとしてブロックされる（Safari・Firefox）ことを避ける。セッションCookieは`SameSite=Lax`。
- Cookie認証の書き込み（`/api/v1/*`のGET以外）は、許可したオリジンからの`Origin`ヘッダーと`application/json`を必須にする（CSRF対策）。ネイティブアプリはBearerトークンを使うため対象外。
- 位置情報・写真の許可は、何を記録するかを説明する画面の後でOSに確認する（3プラットフォームとも初回のみ）。
- Android/iOSは起動時にAPIへ届かなくてもログイン状態を保つ。サーバーがセッションを拒否した（401）ときだけログアウトし、再ログインを案内する。
- Androidの端末バックアップ（Google）には記録DBを含め、セッショントークン（端末のKeystoreで暗号化）・同期状態・写真の割り当て・滞在キャッシュ・記録の診断ログは含めない。リリースビルドは平文HTTPを許可しない（デバッグビルドだけエミュレーターのホストへHTTPを許可）。

写真位置の補正候補は、写真自身を判定材料から除外し、撮影時刻の前後15分以内にある精度100m以下の位置ログをスパイク補正した加工済み座標から線形補間または最近傍で求める。候補はユーザーが適用するまで記録を変更しないが、未確定のEXIF写真の地図・Timeline表示には候補座標を使う。手動指定は地図クリックまたは緯度経度入力で行い、補正済み座標・補正方法・元のEXIF座標を保存する。位置情報を削除した場合も元のEXIF座標は残す。元のEXIFへ戻した場合は自動表示配置を無効化する。

写真ライブラリのインデックスは日付と座標で写真をグループ化しているため、Android/iOSの補正操作は写真グループ単位で適用する。Webの個別インポート写真は1レコード単位で扱う。
